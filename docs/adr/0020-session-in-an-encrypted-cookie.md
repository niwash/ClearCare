# The session is a cookie the Next server encrypts, and the browser never holds a token

Signing in gives the site a session held by Auth.js, the Next.js authentication library shipped as `next-auth` v5, configured with the Cognito provider and the JWT session strategy. The session is one cookie encrypted with `AUTH_SECRET`, marked HTTP-only and `SameSite=Lax`, and `Secure` outside localhost, so the browser carries an opaque value that page scripts cannot read. No access, ID or refresh token is kept: no callback stores one, so the cookie holds only the claims a page is shown. Those are the email address, the name, and Cognito's subject claim, and nothing else.

That shape follows from the criterion that no token be reachable from client JavaScript. A session in `localStorage`, or a token returned from a route handler for the browser to keep, fails it outright. A cookie the server writes and only the server can read passes it, and it is also why the account work needs no change in the Spring Boot API: authentication ends at the Next server, and no Cognito token is sent to the API or stored in the database.

The subject is pinned on sign-in. Without an adapter next-auth gives every sign-in a fresh random user id, which its default token copies into `sub`, so the id a page reads would change for the same person each time and anything keyed on it would lose the account. The `jwt` callback therefore takes Cognito's `sub` from the profile, falls back to the account's provider id, and leaves the token untouched on later reads.

Seven days is the idle limit, not a fixed lifespan. With JWT sessions Auth.js extends the expiry each time the session is read, so an account that keeps visiting stays signed in; an absolute deadline would be a separate claim in the token and a different decision. The cookie is `Secure` and carries the `__Secure-`/`__Host-` prefixes when the request URL is https, which is why the configuration sets `trustHost` and nothing else: the URL comes from the forwarded host the load balancer and Vercel's proxy both set, and an explicit origin variable would silently disable the secure prefixes when it was absent. Where the Cognito variables are missing the site still renders and the authentication routes answer 503, so a checkout without credentials is usable and the failure names itself.

`next-auth` v5 is a pre-release, which is accepted rather than overlooked. `@auth/core`, its engine, would mean writing the cookie, state and callback handling ourselves, which is the same code with fewer guardrails; Better Auth supports Cognito through OIDC, so choosing it would not reopen the identity-provider decision, though it brings its own session store and data model. The beta is pinned to one exact version and contained in one module, so a change of library is a change of that module and the pages that read it. If it never ships, the exit is the same provider and the same two callbacks on `@auth/core`, or the OIDC code flow written directly against the pool, which is small because the provider does the token exchange; staying on an unmaintained beta is not one of the options. The costs are named: a pre-release can change callback signatures between betas, the hosted login means the sign-in page is an explanation and a button rather than a form of our own, and the secure prefix depends on the request arriving as https, so a proxy that drops `X-Forwarded-Proto` would downgrade the cookie rather than fail loudly.

What this record does not decide: the account pages and their controls, the sign-out that leaves for Cognito as well as clearing this cookie, the privacy notice, or the deletion route. Those are separate records.

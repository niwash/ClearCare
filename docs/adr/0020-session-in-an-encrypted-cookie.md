# The session is a cookie the Next server encrypts, and the browser never holds a token

Signing in gives the site a session held by Auth.js, the Next.js authentication library shipped as `next-auth` v5, configured with the Cognito provider and the JWT session strategy. The session is one cookie encrypted with `AUTH_SECRET`, marked HTTP-only and `SameSite=Lax`, and `Secure` outside localhost, so the browser carries an opaque value that page scripts cannot read. Access, ID and refresh tokens stay inside that cookie: they are not projected onto the session a page receives, not written to browser storage, and not logged. A page sees the email address, the name and Cognito's subject claim, and nothing else.

That shape follows from the criterion that no token be reachable from client JavaScript. A session in `localStorage`, or a token returned from a route handler for the browser to keep, fails it outright. A cookie the server writes and only the server can read passes it, and it is also the reason the account work needs no change in the Spring Boot API: authentication ends at the Next server, and no Cognito token is sent to the API or stored in the database.

Seven days is the idle limit, not a fixed lifespan. With JWT sessions Auth.js extends the expiry each time the session is read, so an account that keeps visiting stays signed in; an absolute deadline would be a separate claim in the token and a different decision. The cookie is `Secure` and carries the `__Secure-` and `__Host-` prefixes when the request URL is https, which is why the configuration sets `trustHost` and nothing else: the URL comes from the forwarded host the load balancer and Vercel's proxy both set, and an explicit origin variable would silently disable the secure prefixes when it was absent. Where the Cognito variables are missing the site still renders and the authentication routes answer 503, so a checkout without credentials is usable and the failure names itself.

`next-auth` v5 is a pre-release, which is accepted rather than overlooked. `@auth/core`, its engine, would mean writing the cookie, state and callback handling ourselves, which is the same code with fewer guardrails and no upgrade path. Better Auth is a different data model, with its own session store, and choosing it would reopen the identity-provider decision that chose Cognito. The beta is pinned to one exact version and contained in one module, so a change of library is a change of that module and the pages that import it.

If the beta never ships, the exit is the engine underneath: the same Cognito provider configuration and the same two callbacks on `@auth/core`, with the route handler that already exists keeping its shape, because the surface used here is the provider, the session callback and the cookie helpers. The further fallback is the OIDC code flow written directly against the pool, which is a small amount of code because the provider does the token exchange. Staying on an unmaintained beta is not one of the options.

The costs are named. A pre-release can change its callback signatures between betas, so the pin moves deliberately. The hosted login means the sign-in page is an explanation and a button rather than a form of our own. And the secure prefix depends on the request arriving as https, so a proxy that drops `X-Forwarded-Proto` would downgrade the cookie rather than fail loudly.

What this record does not decide: the account pages and their controls, the sign-out that leaves for Cognito as well as clearing this cookie, the privacy notice, or the deletion route. Those are separate records.

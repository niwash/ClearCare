# A signed-in visitor's saved search is a row, written by the API

The search page remembers a search for a signed-in visitor: the county, the order and the ticked care and amenity options, so they come back on a later visit without being chosen again. It is stored in two tables in `clearcare`: `users`, one row per account, whose `id` is an identity column and whose only identity is Cognito's subject claim; and `user_preferences`, one row per account keyed on that id, holding a single JSON document of the visitor's choices. Splitting them is what makes the second thing the site stores for a person a row that references an account rather than another copy of its subject. The web server reads its own session cookie, takes the subject out of it and sends the subject and a shared token to the API, which writes both rows, creating the account row the first time that account saves anything. A visitor who has saved nothing is answered with null, and `DELETE /preferences` removes the saved search and leaves the account row. The migration in `db/V15` creates both tables and grants `clearcare_api` SELECT, INSERT and UPDATE on `users`, USAGE on its identity sequence, and SELECT, INSERT, UPDATE and DELETE on `user_preferences`; `GET`, `PUT` and `DELETE /preferences` are the only paths that touch them.

This is the first table the API writes, which is the part worth recording. ADR-0010's boundary is between data extracted from HIQA and everything else: the pipeline owns the parse, the transform and the load of what a report says, and the API owns what a visitor does. A saved search is the visitor's own choice and is not extracted from anything, so it belongs on the API's side of that line, and the pipeline is granted nothing here. The grants stay as narrow as the use: four verbs on the saved searches, three on the account rows, and still SELECT only on the views.

The choice lives with the account rather than with the browser, and that is the whole argument for a table. Storing it in `localStorage`, the way the shortlist works (CCARE-127), needs no migration and no release, and it satisfies the same visit on the same browser and nothing after it: a visitor who chose on a laptop and then signs in on a phone would start again. Making the account the store is what the accounts work was for.

The costs are taken rather than argued away. The API cannot check a session, because the browser holds no token it could present (ADR-0020), so a request has to be proved to be the site's another way: the two services share a token (`clearcare/site/token` in Secrets Manager, read as `SITE_TOKEN`), the API compares it in constant time, and a request without it is refused with 401. The token is named for the site rather than for this feature because it proves the caller, not what is wanted, so the next thing the site asks the API for on a visitor's behalf is guarded by the same one. The token is a secret that has to be set before the feature works and rotated if it leaks, and a deployment without one answers 503 while the site hides the controls, so it degrades to the site as it was rather than failing. The account id is personal data of a new kind in this database, though it is only the subject claim: no name, no address and no search terms are stored. The stored document is not validated against the filters, because the API does not know them and should not learn them: the site drops a county the register does not have and an option it no longer offers before it sends anything, the API refuses what could not have come from the page at all, and a saved search written under an older set of filters opens as the search that can still be made.

Three alternatives were not taken. A Cognito custom attribute keeps the preference with the identity provider, but writing it needs either the user's access token, which ADR-0020 deliberately does not keep, or an administrative call the web task has no credentials for. A claim in the session cookie is small enough for a few filters and wrong for the job: a cookie is capped at four kilobytes, is sent on every request, and is gone when the session ends. A second store of its own, outside both the database and Cognito, would be a service to run for one row per account.

What this record does not decide: greeting a visitor by name. That needs the pool to collect `given_name` and `family_name`, and AWS does not allow an attribute to become required after a pool exists, so it is a new pool rather than a change to this one, and it belongs to whoever creates the production pool. Neither does this record decide how a deletion request removes the row: `documentations/designs/account-deletion-process.md` is written and uncommitted, and when that becomes a route it has to delete this row as well as the account.

The saved search opens itself on every visit to `/search` that carries no search of its own, and that includes the visit that arrives from the header link. It must therefore not open on the page that exists because the visitor emptied the filters: "Clear all", and removing the last filter tag, lead to `/search?filtersCleared=true` rather than to a bare `/search`, and that address is what stops the choices being put back in front of someone who has just removed them. The marker is in the address rather than in memory so that a reload or a shared link keeps the page emptied. Forgetting is the opposite instruction and deletes the row before returning to a bare `/search`, which is then empty because there is nothing left to open.

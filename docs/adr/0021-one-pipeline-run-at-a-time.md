# One pipeline run at a time, recorded

A scheduled pipeline task is one run: it starts, does what is due, and stops. Two of them must not write to the database at once, and a migration must not run while one is writing, so a run takes a session-level advisory lock for its whole length, and a run ends with an exit code that ECS and the alarm can act on. Each run also records itself in `clearcare.pipeline_run`, so what ran is a query rather than a search through CloudWatch.

The lock is `pg_advisory_lock(149)` on the connection that also writes the run's row. The number is fixed and recorded here because the migrate task takes the same one; the stages' own advisory locks (31, 34 and 76) are transaction-scoped and allocate a version number, so they cannot collide with it. The lock is taken before the data directory is restored from the bucket: a task that is going to do nothing should not download the whole of `raw/` first, and `pg_try_advisory_lock` says at once whether the run may go ahead. A run that does not get the lock logs that another run or a migration holds it, exits 0, and writes nothing: the schedule starting the task does not know one is already going, and a skipped run is neither a success nor a failure of the pipeline.

The migrate task takes the same lock in `infra/aws/migrate/migrate-with-lock.sh`. Flyway cannot hold a session-level advisory lock for the length of a migration, so the script holds one on a `psql` session and runs `flyway migrate` inside it, and the lock is released when that session ends. `flyway` commands that only read (`info`, `validate`) run without waiting. `bin/deploy` waits for a running pipeline task to stop before it migrates, but that wait is now a courtesy: with the lock held by the migration, a task that starts in between waits for it rather than writing alongside it. Before this, `bin/deploy` failed outright when a task was running, and nothing retried the deploy.

A run's exit code says whether the pipeline is broken:

- `0` the run finished, and everything it was due to do was done.
- `1` a stage failed, an exception escaped a stage, the bucket state could not be restored or uploaded, or a stage read nothing at all out of what it was given.
- `2` the object store's settings are missing or invalid.

Stage exit codes are `clearcare_pipeline.exit_codes`: `0` done, `1` the stage could not do its part, and `3` for work the next run retries. `3` is not a run's exit code. The schedule records the job, and the run, as `incomplete` and exits 0.

`3` exists because two kinds of non-zero answer were being conflated. A crawl stopped by HIQA's browser verification page, or by 429s and 5xxs still there after its retries, used to be retried the next day and still is: making the task exit non-zero for it would alarm nightly for something that needs no one. The same is true of the reports this parser version cannot read (ADR-0013), which fail on every run until the parser grows, of a HIQA response that has no regulation text to split, and of a price list it cannot parse. Those stages answer `3` when they did part of their work, and `1` when they did none: a run that read nothing at all out of everything it was given is the pipeline, not the data. A centre page the parser cannot read, a report that is not a PDF, or a database error is `1` either way. The state file keeps `incomplete` next to `succeeded` and `failed`, and the run's row keeps it next to those.

`clearcare.pipeline_run` has one row per run: `started_at`, `finished_at`, `outcome`, `exit_code`, and the first failure in `detail`. The row is inserted before the run touches anything and updated when it ends, so a task that is killed leaves a row that is still `running` - which is how a run that never ended is told from one that did, since nothing else would leave a trace. A constraint ties `running` to a null `finished_at`, so a row cannot be half closed. The pipeline role gets `SELECT`, `INSERT` and `UPDATE` on it, and no `DELETE`. Nothing reads it yet; when the site shows the last run, it reads a view, like everything else the API sees.

The long-running pipeline of the VM is not a run and takes no lock: it would hold one while it slept. It keeps working as before until the VM goes, against its own database, where no migration is run.

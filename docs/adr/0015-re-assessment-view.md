# Each judgment is compared with the centre's next report

The view `clearcare.next_inspection_result` (db/V4) shows, for each regulation a report judged, what the centre's next report said about it. The next report is the same centre's report with the earliest later inspection date. `next_result` is that report's judgment of the same regulation as printed, `not re-assessed` when the next report does not list the regulation, or `no later report` for the centre's latest report. "Not re-assessed" only means that the regulation is not in the next report we can read. Compliant judgments are included, so the API can show how often each starting judgment was checked again. A report with no inspection date is left out, because it cannot be put in order. A report is also left out when two of the centre's reports share the next date, because neither of them is the next report.

The glossary's re-assessment differs because it goes on past a report that leaves the regulation out until a later report judges it again, and a finding there starts a new re-assessment; this view stops at the next report. Picking one of two reports on the same date by its id would have made the result depend on the order the reports were loaded in. Working the pairs out in the API would have put the definition in Java, where a query in psql cannot use it.

The API reads the view and nothing behind it. Reports that are not loaded, thematic reports among them (ADR-0013), are passed over, so loading a report can change the next report of the one before it. A centre's latest report shows `no later report` until its next report is loaded. The re-assessment trail will be a view of its own in a later migration.

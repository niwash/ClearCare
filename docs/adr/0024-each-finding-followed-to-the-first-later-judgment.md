# Each finding is followed to the first later report that judges its regulation again

The view `clearcare.finding_re_assessment` (db/V14) has one row for each finding of a loaded report. It first reduces each report to one judgment per regulation, as V4 does, and then keeps the Substantially compliant and Not compliant judgments. For each finding it looks for the first later date on which a report of the same centre judges the regulation, with any judgment, Compliant included. If the centre has one report on that date, the finding is `re-assessed` by that report, and `reports_between` counts the centre's dated reports in between, none of which judged the regulation. If the centre has more than one report on that date, the status is `order unknown` and no report is named. A finding is also `order unknown` when its own report has no date. Otherwise it is `not re-assessed` when the centre has later dated reports, and `no later report` when it has none. A later judgment that is itself a finding has its own row, so reading the rows in turn gives the re-assessment trail that ADR-0015 left for a later migration.

Stopping at V4's next report would have lost findings: the next inspection skipped 1,606 of them, and a later report of the same centre judged 655 of those (data of 3 November 2026). Working the trail out in Java or in the web would have put the definition where a query in psql cannot use it, as ADR-0015 says of V4. Ordering two reports on one date by their id would have made the answer depend on the order they were loaded in.

V4 is unchanged, and `/statistics/re-assessment` still reads it. "Not re-assessed" means only that no later report ClearCare has loaded judges the regulation. Undated reports are never later reports, and reports that are not loaded, thematic ones among them (ADR-0013), are passed over, so loading a report can change the re-assessment of an earlier finding. `GET /centres/{centre_id}/findings` reads this view.

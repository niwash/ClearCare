# Price lists are versions, and the newest price wins

HSE publishes the two price lists as PDFs, and republishes them: a centre's price changes between publications, and a list is sometimes issued again for the same date. The centre page needs one price per centre, and the question "did this home get more or less expensive?" needs the earlier ones too. So each loaded file is stored as one `clearcare.contract_price_list` row (home type, record date, version, source file) with one `clearcare.contract_price` row per centre in it. Nothing is overwritten: a later publication or a re-issue becomes another list, and `clearcare.contract_price` keeps the whole series. db/V9's `centre_contract_price` view reads the newest of them for the API, ordered by list date and then version, so the page shows the price in force.

The version is the next number for that home type and date (`max + 1`), taken under an advisory lock so two runs cannot take the same one. The same bytes loaded twice write nothing, because a list is looked up by the file's sha256. A list that has no price for any stored centre is a failure rather than an empty list, so a run made before the register was loaded is not recorded as loaded and can be repeated. The date column is called `record_date` because the public list prints when its prices start and the private list when it was published; `home_type` is kept on the list rather than on each price, since a file is one or the other.

This keeps history without a delta format. A publication that lists only the changed prices would be stored as a version holding just those rows, so a per-centre read stays right while a list-wide read of that date would be short. Version numbers are derived from the stored rows, so deleting a list's rows rewinds the counter, and the next load of that date is version 1 again. Both are accepted for now.

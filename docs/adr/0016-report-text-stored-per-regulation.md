# Report text is stored per regulation and extractor version

We store the opening inspector narrative, each regulation's inspector narrative and each Section 1 provider response in one append-only table. The summaries that open the Capacity and capability and the Quality and safety sections, where inspectors often follow up the last inspection, are stored too, as capacity_summary and quality_summary rows without a regulation. Each row names its report, kind, regulation where applicable, first and last PDF page, and extractor version. A CSV beside the parser mappings defines the text boundaries; registration-regulation headings close a response without being stored. Ingest writes these rows with the report's other records; a backfill command reads stored PDFs for loaded reports that have no text at the current version. The API reads a view, with no access to the table.

Each row also stores an integer array of character offsets where pages after the first start. A single-page row has an empty array. Empty intervening pages share the next page's offset. The API view exposes this array so consumers can place a span on its original pages without reading the PDF or running a newer text mapping.

Keeping only whole sections would make every consumer cut regulations again and recover their page numbers. Separate tables for inspector narratives and responses would repeat the same structure. Replacing earlier text would lose the extraction that a linkage used, so a new extractor version appends rows instead.

Layout changes belong in the mapping. The version is the extractor's own, a constant changed only with the mapping or the extractor, not the deploy's CLEARCARE_PIPELINE_VERSION, so a deploy re-extracts nothing and repeat runs add nothing at that version. Reports whose text cannot be cut are logged with their reason and make the command exit unsuccessfully. A Section 1 response that is absent from the source, or cannot be cut from the text around it, leaves the report and all other text intact, is logged by report, regulation and reason, and makes only backfill exit unsuccessfully, including repeat backfills. The scheduler runs the backfill after ingest, when it starts and after each report download, so nothing is run by hand; it does not change the source PDFs or existing report records.

# The pipeline schedules itself in Compose

The pipeline runs as a long-running service in the root `compose.yaml`, next to the database and the API. A small scheduler, `clearcare_pipeline.schedule`, runs its stages one at a time. It takes a register snapshot once a day, and downloads the inspection reports once a week, or a day after a failed attempt. When it starts, and after every download, failed or not, it copies new files to the bucket if one is set. It loads the register into the database when it starts and after each register snapshot. Before it contacts HIQA, it writes the job's next attempt to a file in the data directory, so a restart cannot bring a crawl forward. `CLEARCARE_CRAWL` turns the downloads on, for one county or for every centre. It is off by default, and then the pipeline only uploads and loads what its data directory already holds.

On the VM, a systemd timer (CCARE-17) takes the register snapshot, and reports are downloaded by hand, one county at a time, so only the VM runs the pipeline on a schedule. The VM keeps its systemd units until it moves to this Compose file in a later change. With the scheduler in Compose, any machine with Docker runs the database, the API and the pipeline with `docker compose up`, and the schedule is Python code with tests, like the stages.

The scheduler's failures show in its log and in its state file. The state file records only the outcome of each download; upload and load failures are only in the log. Jobs run a day or a week after the last attempt, where the timer runs at 06:00 UTC. A stage has no time limit, so one that hangs holds up the others.

A second timer for reports would keep the pipeline tied to the VM. Cron inside the container would start jobs at fixed times, but it would not wait a day after a failed crawl or catch up after the machine was off, so we would still write that code. Crawling is off by default because each copy of the project crawls HIQA on its own, and a fresh clone should not start a national crawl.

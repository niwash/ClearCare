# Centre locations are PostGIS points, and search sorts by distance in SQL

Search can order centres by straight-line distance from a place the visitor picks, and show them on a Google map. Each centre's location is a `geography(Point,4326)` in `clearcare.centre_location`, which `db/V16` creates, the pipeline fills from Google's Geocoding API, and the API only reads. Search orders by `ST_Distance` before it pages, in the SQL it already runs (`CentreSearchRepository`), and on geography that distance is in metres on the WGS 84 spheroid. Installing PostGIS needs a superuser, or `rds_superuser` on RDS, so the administrator installs it. That is a narrow exception to ADR-0010: the migrations still own the table and its grants, and V16 checks that the extension exists.

Computing the distance in Java or in the web needs no extension. But search pages in SQL, so the API would have to load every matching centre and sort them before it could page them, and the web only ever has one page. Plain latitude and longitude columns with the haversine formula keep the sort in SQL, with no extension, no administrator step and no new image. The cost is trigonometry we would write and test ourselves, on a spherical earth. PostGIS gives the distance in one call, and has the bounding-box and nearest-neighbour queries a map is likely to need next.

From now on every database the project runs has PostGIS, and Compose and the tests share one image. The administrator installs the extension before V16 reaches a database and upgrades it with `ALTER EXTENSION postgis UPDATE`; no migration does either. Dumps leave the extension out, and the administrator installs it in the new database before a restore (`infra/aws/README.md`). Google's coordinates may be kept for 30 days at most, so the geocoder replaces or deletes each point before then. There is no spatial index until a query uses one.

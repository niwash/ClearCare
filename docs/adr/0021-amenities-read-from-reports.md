# Amenities are read from reports by a model and stored per report and extraction

We read what a centre offers its residents from its inspection reports: care types, room types, outdoor space, activities, transport, religious services, special units, dining and other notes. A model (gpt-4o-mini) reads the whole report text with structured outputs, so every answer has the same nine fields, and each value is stored with the report it came from. Provider text and inspector observations are not separated yet. The extractor (Research/Data Extraction/extractor.py) is a standalone script that reads the pipeline's manifest and raw store and writes one JSON file per centre. load_amenities matches each file to a stored report by the SHA-256 of its PDF and adds one row to clearcare.report_amenities, keyed by report and extractor version. The API reads the view centre_amenities, which holds the newest extraction of each centre's newest report that has one, and has no access to the table.

A flag is true or false when the report says so and null when it is silent, because a report that does not mention a garden does not show that the centre has none. Transport counts only when the centre provides it for residents; public transport nearby does not. The lists are not normalised yet. The "About the designated centre" section holds much of this information but is not stored as report text (see the comment at pipeline/src/clearcare_pipeline/parser/text.csv line 2). It will be stored later, when the extraction moves into the pipeline.

A model's answer is not ground truth. Before the values are shown as fact, they are measured against a hand-labelled gold set, field by field. Rows are append-only: a re-run at the same extractor version adds nothing, and a changed prompt or model gets a new extractor version, while the view selects by extraction time (extracted_at DESC, then insertion id DESC), not by the version label. GPT-4o-mini is due to leave OpenAI's API on 14 January 2027, so the model and extractor version are stored on every row to tell runs apart.


## V2 integration

V12 adds a separate append-only report_amenities_v2 table, retaining the existing v1 table and view. The four approved lists are stored as JSONB so category-owned evidence passages and page ranges survive unchanged. Explicit filename, source URL, model and extraction timestamp accompany each row; report/source joins retain the PDF hash and report identity. The loader uses the shared contract, checks centre/date/hash against the stored report and validates page bounds against the exact raw PDF. It rejects missing or timezone-naive timestamps for new v0/v1/v2 input instead of fabricating load-time provenance. Existing stored rows are not changed or retrospectively repaired.

The default amenities endpoint remains v1. The explicit query version=amenities-v2 selects the separate v2 view and returns the same centre_id/amenities envelope and report_id, inspection_date, extractor_version and model metadata, with four item/evidence arrays. There is no cross-version fallback. Existing null/404/503 responses remain; unsupported versions return 400. Both views select the newest report with data using the existing ascending report-id tie-break, then extraction time and insertion id. Scheduling and production rollout remain CCARE-171.

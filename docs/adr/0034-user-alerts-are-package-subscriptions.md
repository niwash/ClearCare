# User alerts are package subscriptions, and the account's email stays in Cognito

A signed-in user can ask to be emailed when a new inspection report is published: for one centre, for one county, or for every report on the site. What can be subscribed to is a row in `clearcare.alert_packages`, a generic kind — scope `CENTRE`, `COUNTY` or `ALL`, stored uppercase — with the title and description the site shows. A subscription is a row in `clearcare.alert_subscriptions` for one account, which is the Cognito subject held as `cognito_sub` in `clearcare.users` (ADR-0025, V15), naming one package and holding the target in a `metadata` array of exactly one object: `[{"county_id": 1}]`, `[{"centre_id": "117"}]` or `[]` for the all-reports package. One row per target, so a user who follows Cavan and Dublin has two rows, and a double click or a retried request cannot create the same subscription twice, because a partial unique index on `(user_id, alert_package_id, metadata)` where the row is active compares the normalised jsonb — whitespace and object-key order do not matter — while unsubscribing deletes rows rather than flagging them, so resubscribing cannot collide with history. `deactivated_at` stays, tied to `is_active` by a check, for paths other than unsubscribing that switch a subscription off.

The report ingestion workflow writes what a run matched into `clearcare.alert_events`: one row per package the run matched, each stamped with one `task_uuid` the run generates — per ingest run, not per pipeline run, which also carries the register and the prices (ADR-0022) — and a `metadata` array shaped by the package: the centre package lists the centres the run touched, one object each (`[{"centre_id": "117"}]`), the county package the counties (`[{"county_id": 2}]`), and the all-reports package one object per report pairing its centre with its county (`[{"centre_id": "117", "county_id": 2}]`) — a centre or county the run touched twice is listed once, and an entry without a resolvable county keeps `"county_id": null`. Each event moves from `pending` through `processing` — the claim a dispatcher run makes, and the marker a crashed run must requeue — to `processed`, stamped with `processed_at`, or to `failed` for a retriable attempt; matching nobody is a processed outcome, because per-account skips belong to `alert_notifications`. The dispatcher, still to build, reads the unprocessed events, matches the active subscriptions, resolves each account's address, and records what it told them in `clearcare.alert_notifications`, where `retry_count` carries a failed send to the next attempt on the same row. The table has no unique constraint on purpose: how many receipts a run writes for an account, and whether the dispatcher sends one email per package or one per run, is its decision at runtime, and deduping belongs to that workflow — a key over `metadata` would cap a receipt at a btree page and would read `[1, 2]` and `[2, 1]` as different runs. The schema stays generic this way: report ingestion is the first source of alerts, not the only one.

The recipient's email address is never stored. Cognito owns the account and its address, and the subject claim is the only identity in the database (ADR-0025, V15); the dispatcher resolves the address at send time with Cognito's `AdminGetUser`, keyed by the `cognito_sub` it reads from `clearcare.users`. No table, no request field and no log line carries the address; an account whose address cannot be resolved is marked `skipped` and never retried; a user who changes their address in Cognito is followed from the next send. Unsubscribing has to work without a session, from the link in the email, so the link authenticates by a per-account capability in `clearcare.alert_unsubscribe`: one random token — `gen_random_uuid()`, derived from nothing, so it is not personal data — that the dispatcher creates the first time it composes an email for the account, and that the site's unsubscribe endpoint validates and cancels subscriptions by. The token lives in its own table rather than a column of `users`, so the site's own tables (ADR-0025) are untouched and the whole feature drops with this migration.

A trigger on `clearcare.inspection_report` could have written a report-shaped outbox, one event per report, and left the matching of packages and subscriptions to send time; the ingest workflow writing events per package was chosen because the run's `task_uuid` gives the receipt its grouping and the event already names the package, so the dispatcher matches with a plain join. The address could have been a column on `users` or on the subscription, which would copy into our database what Cognito owns and go stale when a user changes it there; the unsubscribe link could have carried the user id or the subject, which are identifiers, not secrets; a signed URL could have replaced the stored token, which would put a secret into two code bases and make rotating it a release. V26 ships no packages: the three kinds are seeded by V28, with the copy the site shows, so the schema migration stays bare bones — and until V28 runs there are no package rows, no subscriptions and no events; the feature was inert behind its own foreign keys.

A new kind of subscription is a package row and a widened scope check, not a new table; the metadata key each scope reads (`county_id`, `centre_id`) is an agreement between the code that writes it and the code that reads it, checked by the database only as a shape — an array of at most one element, and that element an object; the keys inside it are the API's to sanitize before insert. The scope values are uppercase, and every writer — the seeding task, the API, the dispatcher — must spell them the same way. The dispatcher, the email sending, the subscribe pages and the unsubscribe route are still to build (CCARE-263); the email provider is expected to be SES, with its sending identity and from address still to decide. `alert_notifications` is the only history of what was sent: deleting a subscription does not delete its receipts.

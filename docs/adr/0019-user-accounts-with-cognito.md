# Public accounts are held in a Cognito pool, created by Terraform

Members of the public will create their own ClearCare account with an email address and a password, and the account lives in an Amazon Cognito user pool in `eu-north-1` on the Essentials tier. Cognito owns the credentials: registration, the confirmation email, the sign-in pages and password recovery all happen on its managed login, so no ClearCare screen asks for a password and no table stores one. The pool is declared in Terraform beside the rest of the AWS stack, one module with a root per environment, so development and production are separate pools with their own login domain, callback URLs and app client. This record covers that store and how it is provisioned. What the site does with a signed-in visitor, and the session between the browser and the Next server, is the decision after this one.

The development root creates the pool `clearcare-dev`, its login domain and one confidential app client for the site. Email is the identifier and is verified by the confirmation mail, self sign-up is on, recovery is by verified email, and case is ignored so an address typed in capitals reaches the same account. A password must be twelve characters and carry upper and lower case, a number and a symbol. MFA is off. Access and ID tokens last an hour and the refresh token thirty days, token revocation is on, and user-existence errors are prevented so a wrong address and a wrong password look the same. The only allowed OAuth flow is the authorization code flow, with the `openid`, `email` and `profile` scopes, and callback and logout URLs are matched exactly.

The app client is confidential, so its secret exists in Terraform state. That is why the development root keeps that state in the bucket from `infra/aws/bootstrap` under `cognito-dev/terraform.tfstate`, with encryption at rest and a lock file, and pins the account with `allowed_account_ids`, so an apply in the wrong account fails rather than creating a second pool. `domain_prefix` comes from `terraform.tfvars` instead of a default, because the name is global across AWS and cannot be renamed once the pool exists without replacing the domain; the example file carries a placeholder. An operator reads the secret with `terraform output -raw client_secret`, and the four outputs name the web variable each one fills.

No pool exists in the project account yet. Development runs against a pool in a personal test account, with its state in that folder rather than in the bucket, and creating the project pool is one apply of this root there once the account id and the bucket are settled. Production is a second root over the same module with deletion protection on, because deleting that pool deletes every account, and with SES for its mail once a domain is verified.

The costs are accepted rather than argued away. The client secret is in state, so the bucket's encryption and the account guard are what protect it, and rotating it replaces the app client and signs everyone out. Cognito's default sender allows 50 messages per account per day, so a verified SES domain is a condition of opening registration, not a nicety. Email as the identifier means a second sign-up with an address already registered can disclose that the address exists, though password recovery does not. Managed login version 1 is the classic hosted UI; the branded version 2 needs a branding style per app client and is a change of its own. Callback URLs are exact, so a Vercel preview hostname cannot sign in until it is registered. The module has one real caller until production is applied, which is a small cost and the reason it is extracted now rather than later.

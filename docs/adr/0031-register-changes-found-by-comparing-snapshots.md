# Register changes are found by comparing stored snapshots and kept as typed rows

HIQA's register shows a centre's registration as it is today and keeps no history. We keep a copy from every day (ADR-0007), so the pipeline's `register_changes` stage compares each stored copy with the ones before it and stores every difference as a row in `clearcare.register_change` (db/V21). A register change is a kind and its fields, such as the beds before and after. The words a reader sees are written where the change is shown. There are nine kinds: a registration, a new provider, a new name, a change of beds, an extra condition added, removed or changed, and the Chief Inspector's note added or removed. A centre gets one row of the kind `registration` for each registration number, dated by the registration date. Every other kind is dated by the Irish day on which the copy that first showed it was fetched, because the register does not say when a change happened. A provider change is a change of CRO number, and a provider is named only when it has one, so that only companies are named. The loader also stores each centre's registration number, dates and note, and its extra conditions: every condition numbered 4 or more, and condition 3 when it says more than the maximum number of residents. A scheduled run has every stored copy in its data directory, so the stage reads them all each time and adds only the changes that are not stored yet. The first run after a deployment adds the history, and there is no separate backfill.

We could have worked the changes out in SQL over `register_entry`. The snapshots loaded before V21 have no registration columns there, and comparing conditions needs code: HIQA runs the condition numbers into the words around them, and a sentence inside a condition can name a condition. We could also have stored the whole conditions column with each entry. It is about 500 KB a day, nearly all of it the same three conditions, and the site shows only the extras. The whole column stays in the raw store, where changed rules can read it again.

Rows are only ever added, each with the version of the rules that found it (`RULES_VERSION` in `register_changes/differ.py`). A change to a rule is a new version, and its rows are stored beside the earlier ones, so whatever reads the table has to choose a version. Nothing reads it yet; the API gets a view when it first serves register changes. Except for a registration, a change's date is the day we first saw it, which can be later than the day it happened, and the site has to say so. A stored copy that cannot be read is passed over with a warning, and its changes are then dated by the next copy that can be read. The register can show a renewal months after it started, so a registration whose expiry date has passed is never called a lapse.

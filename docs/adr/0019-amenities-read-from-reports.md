# Amenities are read from reports by a model and stored per report and extraction

We read what a centre offers its residents from its inspection reports: care types, room types, outdoor space, activities, transport, religious services, special units, dining and other notes. GPT-4o-mini does the reading, with structured outputs so that every answer has the same nine fields. Each extraction is one row in an append-only table, clearcare.report_amenities, keyed by report and extractor version. The extractor (Research/Data Extraction/extractor.py) is a standalone script. It reads the pipeline's manifest and raw store, and writes one JSON file per centre. load_amenities reads those files and matches each to a stored report by the SHA-256 of its PDF, the same hash the database keeps in source_file. The API reads a view, centre_amenities, that holds the newest extraction of each centre's newest report that has one, and has no access to the table.

A flag is true when the report mentions the amenity and null when it does not. A report that is silent about a garden does not show that the centre has none, so the extraction only says when something is mentioned and false does not appear in practice. Transport counts only when the centre provides it for residents, because a report noting that a centre is near the Luas or a bus route says nothing about what the centre offers. The lists keep the report's own wording and are not normalised yet.

The "About the designated centre" section is written by the provider and holds most of this information, but ADR-0016 deliberately leaves it out of the report text because it is not an inspector's finding. A separate step, extract_about, stores it after extract_text as kind about under its own extractor version, about-v1. Adding the section to text.csv would have meant a new text version, and split_commitments splits every response row that lacks commitments for its own version, so every commitment would have been saved twice. The new kind needs the kind check and the check that ties a null regulation to certain kinds in db/V5 widened, which db/V11 does. The about rows are not read by anything yet, because the extractor sends the whole report. Sending only that section is a possible later change.

A model's answer is not ground truth. Before the values are shown as fact, they are measured against a hand-labelled gold set, with each field of each home counted as a match, a false negative or a false positive. Until then the API gives them as what the report says, with the report and the extraction that they came from. GPT-4o-mini is due to leave OpenAI's API on 14 January 2027, so the model will change. The model and extractor version are stored on every row so that results from different runs can be told apart, and a later run is a new row that the view prefers, not an overwrite.

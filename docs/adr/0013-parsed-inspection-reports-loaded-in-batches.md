# Parsed inspection reports are loaded by the pipeline in batches

Each HIQA inspection report is read in two mapping-driven steps, and the values are written to PostgreSQL by the pipeline. The parser splits a report into sections using a CSV mapping (`mapper.csv`); a second mapping (`fields.csv`) reads the cover values and the record tables out of those sections. Both are data, so a change to a report's layout is an edit to a mapping, not to the code. A transform step then turns the parser's output into the rows the database stores: it derives the register's numeric centre ID from the printed `OSV-nnnnnnn`, reads the report's dates and times as `date` and `time`, and splits a regulation into its number and title. The pipeline writes the rows a batch at a time, each batch in its own transaction, so a run over thousands of reports is never one transaction (ADR-0010).

The reports are stored in their own tables: `inspection_report`, with one child table for each record group a report prints (inspectors, regulations, the compliance plan). A report points at the raw PDF it was read from (`source_file`, ADR-0007) and at the centre it is about (`centre`). The ingest creates neither: the downloader records each stored PDF and the register loader records each centre, so the workflow only reads them. That also makes it safe to run again, since a report whose file or fieldwork is already stored is left out.

The cost is that the mappings describe only the standard inspection report. HIQA also publishes "restrictive practice" thematic reports, which use a different template and carry no Centre ID in the sections the mapping reads, so the ingest skips them. Covering them needs a mapping of their own. The ingest also depends on the downloader and the register loader having run first, because it creates neither of the rows it references.

The decision was taken to keep the report's layout in the mappings rather than in the parser, so that a layout change is a mapping edit and not a code change and a review. The decision was also taken to keep reading a report and storing it apart, with the transform as the one place where the report's printed formats become the database's types.
